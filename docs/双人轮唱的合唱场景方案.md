# 基于 ZegoExpressEngine SDK 实时合唱能力的双人轮唱场景方案

## 场景说明
多个用户，在一个业务房间内，分成两个小组（比如A，B），演唱同一首歌，A 组先开始演唱，在歌曲的某一个时间点，演唱人员由 A 组切换到 B 组

## 核心需求

### 同步性

#### 同时开始
即参与演唱的所有用户，在某种程度上应该是同时开始的（需要将网络延时纳入考虑范围内），

#### 进度与歌词同步
在整个演唱的过程中，参与演唱的这些用户应该也是同步的 -- 最简单的衡量办法， 未参与演唱的用户（即观众）听到的演唱的人声应该是保持一致的
同时，所有用户本地显示的歌词应该也是同步的（歌词本身也是受进度驱动）

#### 人声与伴奏同步
即演唱的人声，应该与伴奏是处于歌曲相同的位置

### 平滑过渡
在切换的过程中，需要确保在听众的角度，听到的歌曲的是不会受到影响的，切换的小组之间，也没有进度上明显的差异，整个切换的过程应该是平滑的


#### 推流与限制逻辑
1. 实际上麦上最多会有 4 条流，即 team:A 会推 主路，辅路两路流，team:B 也会推主路，辅路两路流
2. 但是每种角色需要拉的流有区别 - 根据当前是否在推流来决定如何拉流：
    1. 如果是主播，也就是当前在推流的人，仅需要拉辅路流-纯人声流-带"\_aux_\"标记的流
    2. 如果是观众，也就是当前没有在推流的人，仅需要拉主路流-人声+伴奏-带"\_main_\"标记的流
3. 能否推流需要判断当前房间是否存在流,流是否合法-streamExtraInfo中是否包含队伍信息
    1. 房间内没有流 -- 肯定可以推流，推流以后，需要在两路流中都更新 streamExtraInfo 中的队伍信息
    2. 房间内有合法流，且包含的队伍只有一队 -- 可以推流，推流以后更新对应的队伍信息
    3. 房间内有合法流，且包含的队伍有两队 -- 不可以推流，点击上麦按钮有提示
4. 不能仅靠房间内的流的数量来判断能否推流，而是要综合判断

### 拉流

#### 拉流人声对齐
1. 通过 onRoomStreamUpdate 回调来接收房间内的流更新回调
    - 通过判断 updateType 来确认当前回调的是新增流（即有人推流）还是删除流（即有人停止推流）
    - 新增流则 startPlayingStream 拉流
    - 删除流则 stopPlayingStream 停止拉流
    - 拉流前需要判断当前是否支持拉流（即房间内有限制，最多同时存在两条流），通过判断 StreamExtraInfo 是否标识了 team:A 或者 team:B 来判断是否是合法流，是否可以拉流
2. 通过 setPlayStreamsAlignmentProperty:.try 来配置拉流对齐 -- SDK 的能力

#### 进度对齐配置
1. 通过 onPlayerSyncRecvSEI 接受推流侧发送的 sei
2. 解析 sei 内容
3. 通过 sei 内的字段，来实现各自的对齐工作：
    1. 对于正在推流的用户：
        - 通过 currentSong，来对比当前播放的歌曲是否一致，那么怎么其他人点歌，其他人怎么知道点的是哪一首歌呢？还是通过 SEI，SEI 的发送从点歌开始，在停止播放，播放结束回调两个时机结束，当一个主播点歌的时候，记录一下点击确定按钮的时间戳，pickerSong 回调的时候，把时间戳也回调过来，然后也添加到 sei 中，用于防止两个用户同时点歌时候的竞争 -- 当前只是一个 demo，没有什么业务后台，这是一种临时方案
        - 判断点歌的时间戳，更早点歌的人生效，更晚点歌的人需要取消点歌，将点的歌曲换成更早点歌的歌曲信息
        - 然后就可以播放器 load 并开始播放、
        - 同时如果最终竞争失败，自己不是当前唱歌的人，需要 mutePublishStreamAudio 来 mute 两个通道，isSinging 字段修改为 false（默认也是 false）
        - 收到通过 sei 中的 currentProgress，并对比当前播放的进度，如果两个进度差的绝对值，大于 100ms，那么则需要对齐进度，本地需要操作播放器 seek 到 sei 中的进度
        - switchTimeStamp 这个字段我们放到 后面的切换逻辑解释
    2. 对于观众
        - 判断收到的 sei 的里面，哪个 isSinging 为 true，并同步 currentSong，totalDuration, currentProgress 等信息

### 切换

#### demo临时方案
在点歌，并获取了歌曲总时长后，总时长除以 2，并在这个结果的 ±10000ms 附近，生成一个随机数，作为切换的时机
同时更新 sei 中的 switchTimeStamp 字段

经过前面的点歌竞争，等逻辑以后，最后所有人都以 isSinging:true 的用户的切换时间戳为准

当歌曲播放进度超过切换时间戳以后，isSinging 状态，两个推流者的 SEI 重要进行变化
同时，根据 isSinging 的值，两个推流者的 mutePublishingStreamAudio 状态也会变化，即 isStringing: true → false 的推流者，mutePublishingStream 的 mute 状态 false → true，另一个推流者则相反

要确保这个切换只会发生一次 -- 因为 SEI 一直在发送，如果不进行判断的话，那么后续每发送一次 sei，则都要来一次切换逻辑，那么体验就不好
